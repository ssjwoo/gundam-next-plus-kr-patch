# 연구 노트

## 영문 팬 패치 비교

- 팬 패치는 주로 EBOOT 내 CP932 고정 슬롯을 ASCII로 덮어쓴 방식이다.
- USRDIR 자료는 일본판과 바이트 단위로 동일했다.
- 별도 폰트 삽입이나 텍스트 디코더 변경은 없었다.

## 한글 폰트와 인코딩

- `jpn0.pgf`: 한글 완성형 글리프 0개
- `kr0.pgf`: U+AC00..U+D7A3 11,172자 존재
- 폰트 언어 선택을 일본어 1에서 한국어 3으로 변경했다.
- 디코더: VA `0x089BC550`, 원본 함수 크기 `0x48`
- ASCII는 1바이트, 한글은 2바이트로 변환한다.
- `81 A5` 쌍은 원본 UI의 `▼`와 U+ACA5가 충돌하므로 현재 예외 처리 실험 중이다.
- 원본 함수는 `0x08804C84`로 읽은 코드를 런타임 테이블 `0x08D91674`에 조회해 반환했다. 이 테이블은 `0x089BC1D4(0)`이 호출될 때 만들어지며, 현재 디코더는 조회와 생성 호출을 모두 건너뛴다.
- 같은 계열의 다른 함수 `0x089BC598`은 테이블 조회 방식을 그대로 쓴다. 일시정지 메뉴의 `ゲームに戻る`처럼 이 경로로 그려지는 문자열은 지금도 일본어로 정상 표시된다. 문자열마다 렌더링 경로가 다르다.

## 텍스트

- EBOOT 워크북: 7,283행, 665그룹
- 부분 영문판 변경으로 확인한 행: 1,676개
- 직접 포인터 근거가 있는 행: 2,345개
- 현재 로컬 개발 워크북의 한글 초안: 1,543개, 독립 승인 0개
- 고정 슬롯 빌드는 용량 초과를 거부하며 기존 포인터를 유지한다.
- 최신 개발 빌드에서 직접 포인터 필드 2,595개를 재검증했고 계획 밖 변경은 0바이트였다.

### 넥스트 플러스 미션 레코드

- 일본판 복호화 EBOOT의 파일 오프셋 `0x0028ED18`부터 미션 문자열 레코드 274개를 포인터 체인으로 검증했다. 복호화 EBOOT SHA-256은 `ce917a0f7289ccce3a0db8f0783529f93ff31789c0ee0bb1842ce632f0dd0c06`이다.
- 각 레코드는 CP932 문자열·NUL·4바이트 정렬·44바이트 메타데이터·문자열 시작 주소를 가리키는 리틀엔디언 32비트 포인터 순서다. 274개 전부 디코딩·자기 포인터·줄바꿈 세 개를 확인했다. `0x00297490`부터는 구조가 바뀐다.
- 기존 EBOOT 인벤토리와 시작점 208개가 일치하며 66개는 새로 발견했다. 따라서 7,283행 워크북의 미해결 수치와 274개 미션을 단순 합산하지 않는다.
- 2026-09-25에 274건의 한글 초안을 작성해 검증했고, 그중 271건을 전용 삽입기로 개발 빌드에 넣었다. 나머지 3건은 아프사라스 표기 이관 결정이 필요해 `needs_term_decision`으로 보류했다.
- 삽입 빌드는 ELF SHA-256 `64823a33794bcaa7f1f2f1b01d238f24a136805d444d8b6349e4f25dca4ed189`이며, 미션 포인터 274개와 메타데이터 274개를 다시 읽어 검증했고 계획 밖 변경은 0바이트였다. 원문·원시 바이트가 담긴 번역 인계 패키지는 로컬에만 보관한다.

### 지도·설명 99건

- 넥스트 플러스 모드의 지도·설명 미해결 99건(직접 포인터 81건, 포인터로 복구한 제목 17건, 구조 확인 대기 1건)도 같은 날 초안을 작성했다. 98건이 자동 적용 대상이고 나머지 1건은 구조가 확정되지 않아 적용하지 않는다.

## ISO 구조

- 원본과 개발 빌드는 모두 19파일이다.
- 18파일은 동일하고 `/PSP_GAME/SYSDIR/EBOOT.BIN`만 변경됐다.
- EBOOT의 LBA는 544로 유지됐다.
- 전체 ISO 크기는 원본과 동일하다.

## PZZ·GIM

- PZZ 2,125개 중 2,125개 파싱 성공, 오류 0개
- 페이로드: EMPTY 122, GIM 3,123, HITS 273, PMF2 2,766, SAD 201, UNKNOWN 1,104
- GIM 표면: Index4 680, Index8 3,592, 합계 4,272
- PZZ는 XOR·zlib·고정 블록 할당 구조로 조사됐다.
- 재패키는 원본 할당 초과를 거부하고 변경하지 않은 페이로드의 해시를 재검증한다.
- GIM 교체기는 크기·팔레트·변경하지 않은 픽셀 인덱스를 보존한다.
- 전체 4,272개 GIM 표면을 렌더했고 출력 경로 중복 및 렌더 오류는 0개였다. 이는 텍스트 유무 전수 분류나 이미지 한글화 완료를 뜻하지 않는다.

## 런타임 검증

- PPSSPP v1.20.4 개발 빌드에서 한글 표시 PoC 성공
- `파일럿 이름을 입력하세요`와 `파일럿 이름을 입력하지 않았습니다`를 실제 소비자 경로에서 확인
- 실제 이름 확인 다이얼로그, 전체 문자 범위, 실기 PSP는 미검증
- 로컬 개발 v4 ISO에서 넥스트 플러스 선택 설명 다섯 줄이 화면 안에 표시되는 것을 확인했다.
- 로컬 개발 v5 ISO에서 **첫 번째 스테이지만** 순회했다. 미션 1의 제목과 설명 두 줄, 지도 라벨, 모드 설명, 안내 패널이 한국어로 표시됐다. 삽입한 미션 레코드가 실제 소비 경로에서 그려진 첫 확인이다. 다른 스테이지와 실기 PSP는 검수하지 않았다.

## 반각 ASCII 미표시 결함

- 화면 증거: `NEXT-PLUS 모드의`는 ` 모드의`로, `여기서 MS를 조종하며,`는 `여기서 를 조종…`으로, `2인 협력 플레이도 가능!`은 `인 협력 플레이도 …`로 표시됐다.
- ASCII 구간은 글리프도 자리 폭도 남기지 않는다. 뒤따르는 공백은 남는다.
- 저장된 바이트는 정상이다. 해당 슬롯에는 `4e 45 58 54 2d 50 4c 55 53 20 …`가 들어 있다. 빌드가 아니라 렌더링 경로 문제다.
- 디코더 워드만 바꿔 끼우는 프로브를 세 번 실행해 범위를 좁혔다.
  - 1바이트 문자를 전각(U+FF01~U+FF5E)으로 넘기는 안: `2`는 여전히 아무것도 그리지 않았다. U+FF12도 이 경로에서 그려지지 않는다.
  - 1바이트 문자를 U+AC00으로 반환하는 안: 화면에 `가인 협력 플레이도 …`가 나왔고 `모드입니다.`의 마침표 자리에도 `가`가 찍혔다. **ASCII 바이트가 디코더까지 도달하며 커서 전진도 정상이다.**
  - ASCII를 원본 계열 함수 `0x089BC598`로 꼬리 호출하는 안: 한글은 정상이지만 `2`는 다시 아무것도 그리지 않았다.
- 결론: 이 경로에서 확실히 그려지는 것은 한글 음절 U+AC00~U+D7A3뿐이다. 반각(U+0032)도 전각(U+FF12)도 글리프가 없다.
- 원본 일본어 메시지 문자열은 반각 영숫자를 거의 쓰지 않고 전각 영숫자(`２人`, `ＭＳ`, `６０秒`)를 쓴다. 실제 문장 5,616행 중 반각 영숫자를 포함한 것은 디버그 문자열뿐이었다.
- 기존 초안도 같은 피해를 입는다. 2026-09-25 초안 기준 미션 274건 중 272건, 지도 99건 중 66건이 반각 ASCII를 포함한다.
- 남은 질문은 렌더러가 숫자·영문에 대해 어떤 코드를 받아들이는가이다. 2026-09-26에 이 질문에 답했다: 디코더 값도 폰트 데이터도 원인이 아니며, 메시지 경로가 한글 음절만 그린다. 자세한 근거는 아래 ‘영문·숫자를 살릴 수 있는가’ 절에 있다.

## 영문·숫자를 살릴 수 있는가 (2026-09-26 조사)

결론: **지금 방식으로는 안 된다.** 이 텍스트 경로는 한글 음절 U+AC00~U+D7A3만 그린다.

확인한 것:

- **디코더 값은 원본과 같다.** 원본 ISO를 실행해 PPSSPP 디버거의 `cpu.evaluate`로
  런타임 테이블 `0x08D91674`을 직접 읽었다. `table[0x32] = 0x32`, `table[0x41] = 0x41`로
  ASCII는 자기 자신으로 매핑된다. 원본 디코더도 같은 값을 반환했을 것이다.
- **폰트 데이터는 정상이다.** `kr0.pgf`의 문자 포인터를 직접 파싱했다.
  U+0030 → 글리프 16(`0xDF`), U+0032 → 18(`0xFF`), U+0041 → 33(`0x200`),
  U+FF12 → 13761(`0x5A19D`). 모두 실제 글리프 데이터를 가리킨다.
- **디코더 호출부** `0x088838F4`는 반환값을 `andi 0xffff`한 뒤 `0x7E`('~')와 비교하고
  `slti at, s0, 0x100`으로 0x100 미만을 따로 다룬다. 0x100 미만은 제어 문자로 취급된다.
  (`~f0` 같은 표기가 실제로 게임 형식이라는 뜻이다.)
- **그려지는 범위 실측**: 디코더의 한글 기준값만 바꿔 같은 화면을 비교했다.
  - 기준값 U+AC00 → 한글이 정상으로 그려짐
  - 기준값 U+3041(히라가나) → 패널이 비어 버림
  - ASCII를 U+FF12(전각)로 반환 → 아무것도 안 그려짐
  - ASCII를 U+AC00으로 반환 → `가`가 그 자리에 그려짐
- 반면 **게임 자체 HUD 경로**는 같은 `kr0.pgf`로 `Lv. 1`, `COST 2000`, `500GP`,
  카운트다운 숫자를 잘 그린다. 폰트가 아니라 메시지 경로의 문제이다.

즉 폰트 언어를 한국어로 바꾸면 한글을 얻는 대신 그 경로에서 영문·숫자를 잃는다.
영문·숫자를 되살리려면 메시지 경로가 코드를 글리프로 바꾸는 지점을 찾아 고쳐야 한다.

추적 기록(2026-09-26):

- 폰트 스텁: `sceFontGetCharInfo 0x08A00880`, `sceFontGetCharGlyphImage 0x08A00870`,
  `sceFontFindOptimumFont 0x08A00858` (PPSSPP 디버거 `hle.func.list`로 확인).
- 폰트 언어를 정하는 곳은 `0x089BC3E0` 한 곳이다. `fontStyle.language` 1→3, 이후
  `sceFontSetAltCharacterCode(font, 0x25A1)`.
- 문자마다 폭/글리프 함수 `0x089BC5EC`를 거치고, 144슬롯 문자 캐시(`0x08DB1674`)를 쓴다.
  코드 `0x100` 미만은 폭 0.5, 이상은 1.0이다.
- 브레이크포인트 추적으로 요청 코드 690건을 모았다. `U+0021 !`, `U+0042 B`, `U+0047 G`,
  `U+004D M`, `U+FF0F ／` 같은 코드도 정상 요청된다. 파이프라인이 ASCII를 버리는 게 아니다.
- 따라서 실패 지점은 `sceFontGetCharInfo`/`GetCharGlyphImage` 결과다. `kr0.pgf`가
  한글 이외 코드에 유효한 글리프·메트릭을 주지 않는 것으로 보인다. 확정에는
  `0x089BC708`에서 ASCII와 한글의 charInfo를 비교해야 한다.
- 참고: PPSSPP 디버거 `cpu.evaluate`의 `[주소]`는 10진수 주소를 0으로 읽는다. 16진수로 넘겨야 한다.

## 표기 정책 (2026-09-26)

- 영어는 되도록 영문 그대로 쓰고, 한자·일본어만 한국어로 적는다.
- 숫자·영문이 다시 그려지므로 `숫자 → 한글 수사` 우회는 되돌렸다. 원래대로 `60초`, `3기`로 적는다.
- 이미 그려지는 숫자와 이름·기체·연도 표기는 손대지 않는다. 미션 10건(`제4소대`, `F91`, `M1`, `제08MS소대`, `V2`, `사이드 6/7`)과 지도 8건(`우주세기 0079`, `123년`, `서기 2307년`, `기동전사 건담 0080/0083`)이 남아 있다.
- 넥스트 플러스 초안과 개발 워크북 기존 초안 30행에 적용했고, 메인 메뉴 안내문이 `인 협력 플레이도 …`에서 `두 명이 협력 플레이…`로 바뀌는 것을 화면으로 확인했다.
