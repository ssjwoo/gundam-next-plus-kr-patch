# 최신 판정 — 023 사용자 프리징 해결 확인

2026-10-03 사용자가 “내가 수정요청한거 전부 반영됬고, 미션중 프리징도 해결 됨”이라고 확인했다. 대화의 최신 후보인 023에 대한 요청 수정 수용·미션 프리징 해결을 `USER_REPORTED_PASS / RESOLVED_USER_REPORTED`로 기록한다. 이번 확인에서 파일명·해시·기기별 결과·반복 횟수는 별도로 제공되지 않았다. 023의 EBOOT·폰트·미션은 022와 동일하며 로고는 원본으로 복원됐다.

해당 보고로 미션 프리징 문제를 닫는다. 분류표 손상이 전투 프리징으로 이어진 구체적인 실행 경로는 별도로 증명한 것이 아니며, 게임 전체 검수 완료 판정도 아니다. [023 릴리스 안내](RELEASE_2026-10-03_023.md).

# NEXT PLUS 전투 중 프리징 — 022 수정 후보

사용자는 NEXT PLUS 「타이거바움의 침입자」 미션에서 전투 화면 진입 후 플레이하다가 불규칙하게 게임이 완전히 멈춘다고 보고했다. 여러 번 재시도해도 발생했다. 제공 사진은 PSP 실기이며 미션 선택·출격 로딩·전투 화면을 보여준다. 현재 배포본 021을 조사 기준으로 삼았지만 이번 보고에서 정확한 ISO 파일명·해시를 별도로 재확인한 것은 아니다.

이 오류는 `NEXT_PLUS_MISSION_FREEZE_021`로 기록하며 **실제 해결 여부는 확인 전**이다. 021의 첫 부팅 성공과 이전 `BOOT_LOADING_020` 수정 결과는 별도 관찰로 유지한다. 첫 로딩 수정이 전투 중 프리징까지 해결했다는 주장은 하지 않는다.

## 확인한 데이터와 별도 결함

원본 포인터 체인 기준 미션 ID는 `NPMIS_0018`, 기존 스캐너 ID는 `EBOOT_07602`다. 표시 제목을 공개 번역 초안의 ID만으로 원본 레코드에 연결하지 않았다. 실제 원본 위치 `0x28F53C`와 포인터 `0x28F5C0`를 확인했으며, 021의 44바이트 미션 메타데이터와 포인터는 원본과 같다. 이것이 게임 진행 전체의 정상 동작을 증명하지는 않는다.

폰트 경로를 넣는 도구는 `.data`에서 처음 발견한 64바이트의 0 구간을 사용했다. 그 위치 `0x08A01FFD`는 빈 공간이 아니라 **문자 분류표 `0x08A01F7C`의 확장 바이트 영역**이다. 원본의 EOF 항목과 256개 문자 항목을 포함한 257바이트 배열은 [PSP newlib의 문자 분류표](https://github.com/pspdev/newlib/blob/master/newlib/libc/ctype/ctype_.c) 및 [분류 비트 정의](https://github.com/pspdev/newlib/blob/master/newlib/libc/include/ctype.h)와 일치한다.

경로 문자열의 38개 비어 있지 않은 바이트가 문자 값 128~165의 분류를 덮었다. 게임의 실제 `0x08809304` 함수는 이 표를 읽어 공백 여부를 판정한다. 원본·021·022 각각의 입력 값 0~255를 격리된 MIPS CPU에서 실행한 결과, 021은 상위 바이트 13개를 원본과 달리 공백으로 판정했고 022는 256개 결과 모두 원본과 일치했다. 이는 **분류표 손상의 직접 증거**이며, 해당 미션에서 프리징으로 이어지는 실행 경로를 증명한 것은 아니다.

## 022에서 바꾼 것

`tools/repair_font_path_ctype.py`는 해시가 일치하는 원본과 021 ELF만 받아 원본 분류표를 복구한다. 폰트 경로는 기존 폰트 초기화 함수의 내장 폰트 선택용 영역에 넣고 명시적인 분기로 문자열을 건너뛴다. 파일을 직접 여는 기존 `sceFontOpenUserFile` API·파일 모드·오류 결과 주소·폰트 핸들 저장 경로를 유지한다. ELF 파일 크기·헤더·로드 세그먼트를 늘리거나 다른 0 구간을 빈 공간으로 추정하지 않는다.

021과 022의 폰트 초기화 구간을 서로 다른 스택 위치·라이브러리 핸들 16개 조건으로 실행해 총 32개 사례에서 파일 경로·호출 인자·폰트 핸들 저장과 스택 포인터를 대조했다. 외부 API는 검사 목적의 가짜 함수이며 **실제 PSP 폰트 로딩이나 게임 실행 검증은 아니다**.

기존 `tools/build_userfont_iso.py`도 같은 초기화 블록을 사용하도록 수정했다. 새 빌드에서 임의의 0 구간을 검색하는 방식을 제거하고 원본 분류표를 보호한다. 새 PoC 입력으로 실제 빌더 진입점을 실행하되 ISO 쓰기만 검사 함수로 대체해, 분류표 보존·022와 같은 초기화 블록 생성·너무 긴 경로 거부를 확인했다. 이 검사에서도 게임이나 추가 ISO를 실행·생성하지 않았다.

022 ISO는 021 복사본의 EBOOT 내부에서 총 135바이트만 바꾼다. ISO 전체의 나머지 바이트는 021과 같고, 폰트 파일·미션·이미지·압축 아카이브와 파일 배치를 보존했다. 따라서 새 이미지 작업과 혼합하지 않고 이 결함 수정의 효과를 사용자 실행으로 비교할 수 있다.

ISO CRC32는 `C88A9CA8`이다. 산출물은 로컬 `build/graphics_revision_2026-10-02`에 보관한다. 원본 일본판 ISO 기반 차분의 재적용 결과를 스트림으로 해시 계산해 022의 크기·SHA-256과 일치함을 확인했으며 중복 ISO를 생성하지 않았다. 적용 원본은 SHA-256 `a00c38959d52377b65f9afb5223e02c4ac5a876b8a33c998a7fe3f07dbf1feb3`다.

## 다음 판정과 공개 상태

사용자가 **022 ISO로 같은 미션을 2~3회 끝까지 진행**하고 프리징 여부를 확인해야 한다. 첫 부팅과 한글 메뉴 표시도 함께 확인한다. 증상이 없어지면 해당 조건에서 수정 효과를 기록하고, 계속 발생하면 같은 022를 보존한 채 미수정 실행 경로·원본 비교·호환되는 에뮬레이터 오류 로그로 원인을 더 좁힌다. 무작위 프리징의 짧은 성공 관찰을 전체 게임 정상으로 확대하지 않는다.

021 공개 릴리스에는 후속 프리징 경고를 추가했다. 022는 **비공개 수정 후보 / runtime NOT_TESTED**이며 해결 완료나 새 배포본으로 승격하지 않았다. 기존 021 ISO·xdelta는 보존한다. 게임·에뮬레이터 및 종료된 CMD 검증을 AI가 실행하지 않는다.

로컬 근거는 `work/mission_freeze_021_2026-10-03`의 입력 ELF, 미션 식별, 문자 분류표 참조, 격리 함수 비교 기록과 `font_path_repair_022.json`이다. ISO 읽기 기록과 차분 재적용 영수증은 022 manifest 및 `xdelta_roundtrip_022.json`에 있다. 공개 집계는 `reports/mission_freeze_021_2026-10-03.json`이며 원본 자산·코드 덤프·사용자 사진은 업로드하지 않는다.
